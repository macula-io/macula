# UCAN, macula 12: the vectors

The contract every Macula SDK implements for UCAN-gated procedures (D7), and
normative where the design's text differs. The reference implementation is
`src/auth/macula_ucan.erl`; `ucan_v1.json` holds the vectors, generated by
`scripts/generate-ucan-vectors.sh` from `macula_ucan` itself, and
`test/macula_ucan_vectors_tests.erl` re-derives every verdict from the file on
each run, so the file and `macula_ucan` cannot drift apart.

ML-DSA-87 signing is hedged and pq_hybrid's RSA-PSS half is randomized, so
running the generator again mints other tokens with the same verdicts. The
committed file is the vector.

## What an SDK must pass

For each profile (`pq_pure`, `pq_hybrid`) and each case:

1. `authorize(token, policy, context)` reaches exactly `verdict`: `ok`, or the
   refusal named. The context's proofs are the case's `proofs`, keyed by their
   proof ids.
2. `proof_id(token)` is the `proof_id` given, for every entry of `proof_ids`.
3. For every key in `keys`, the key its `did_key` decodes to has that
   `key_id`, and, where one is given, that `node_id`.

And for every entry of `covers`, `covers(parent, child)` is the value given.

And `did_key_length` (macula#87): a did:key whose text after `did:key:z` is
longer than `max_encoded_chars` (4,400) is `malformed`, refused before it is
decoded, in both profiles; `over_bound` is one character past it. Base58
decodes in time quadratic in its length, and a token's `iss` is decoded before
its signature is checked, so without the bound a caller chooses how much CPU a
provider spends. The longest did:key of a carried key, pq_hybrid's, is about
4,270 characters.

Every refusal `authorize` can reach appears in both profiles.

An SDK that mints tokens checks them by round trip and against macula:
`macula_ucan:authorize/3` must accept a token the SDK mints for the policies
and contexts above. A minter refuses a window no verifier accepts, naming the
values it compared: an `exp` more than the max lifetime past the time of
minting, or an `nbf` not before `exp`.

## The token

A JWT: `header.payload.signature`, each part base64url without padding. The
signature is the issuer's node key's signature, in its profile, over
`header.payload` exactly as they are sent. A verifier checks it over the bytes
as received, never over re-encoded JSON.

- Header: `{"alg", "typ": "JWT", "ucv": "0.10.0"}`. `alg` is `ML-DSA-87` in
  pq_pure, and `ML-DSA-87-PS384` (the LAMPS composite
  `id-MLDSA87-RSA4096-PSS-SHA512`) in pq_hybrid. A header whose `alg` is a
  string but which is not exactly the profile's `alg` with `typ` `JWT` and
  `ucv` `0.10.0` is `wrong_algorithm` (another `typ` or `ucv` included); a
  header with no string `alg` is `malformed`.
- Payload:
  - `iss`: `did:key:z` + base58btc (Bitcoin alphabet, each leading zero byte a
    leading `1`) of the unsigned LEB128 varint of the key type, then the key
    as carried. The key type is `0x1212` (mldsa-87-pub) in pq_pure and
    `0x300087` (Macula's, private-use) in pq_hybrid. A key that is not
    well formed for the profile is `malformed`.
  - `aud`: the lowercase hex of the node_id of the node that presents the
    token. It must equal the request's verified caller: `not_the_audience`
    otherwise.
  - `cap`: a list of `{"with", "can"}`.
  - `exp`: seconds. At or past `exp` the token is `expired`. An `exp` more
    than the max lifetime, 315,576,000 s (ten years of 365.25 days), past
    `now` is `exp_beyond_max_lifetime`; one exactly at the bound is valid.
    UCAN_V1 has no revocation, so this is the only bound on a token's life:
    a token minted with an `exp` in milliseconds authorizes nothing, rather
    than everything for tens of thousands of years. Every link of a chain
    is held to it.
  - Optional `nbf` (before it, `not_yet_valid`), `nnc`, `fct`, `prf`.
  - `iss`, `aud`, `cap` and `exp` must have their types before anything is
    verified: `malformed` otherwise. `exp` is required: a token without one
    is `malformed`, never a token that does not expire.

A key's node_id and key id, and the key as carried in each profile (the
pq_hybrid composite's ML-DSA-87 and RSA halves), are macula's
`macula_node_keys` (`node_id/2`, `key_id/2`, `public_key/1`); an SDK checks
its own against the `keys` table.

## Policies

- `ucan_required` names an issuer node_id: the chain's root must be signed by
  the identity key whose node_id it is (`not_the_issuer`). It names no `can`:
  any `can` answers a request, and the chain then holds it fixed.
- `realm_member_required` names a realm key's key id and a `can`: the chain's
  root must be signed by that key, and the capability must have that `can`.

## Capabilities

A `with` is an MRI: `mri:realm:<realm>`, `mri:org:<realm>/<org>` or
`mri:proc:<realm>/<procedure>`, where a procedure's org is the text before its
first `/`. A realm name is at least one segment, segments joined by single
dots, each of `a-z`, `0-9`, `-`, `_`; case is never folded
(`realm_name_not_canonical`). A procedure grant without an org is
`procedure_without_org`, and so is a request whose procedure has none.

A request's realm id is SHA-256 over a grant's realm name, so a grant is
checked against the request's realm id with nothing looked up
(`wrong_realm` when it names another realm). Narrowing (`covers`): a realm
grant covers its realm, an org grant covers that org and its procedures, a
procedure grant covers only itself. No capability that covers the request is
`missing_capability`.

A context with no realm and procedure checks the token alone.

## Chains

`prf` names at most one parent (`chain_not_linear`) by its proof id: the
lowercase hex of the SHA-384 of the parent token's bytes as they travel. The
parents travel in the request's caller-signed `proofs`, keyed by proof id. A
named parent that did not travel is `missing_proof`; a proof no link names is
`unreferenced_proof`, which a provider answers `malformed_frame`, not
`unauthorized`.

Each parent is checked as a token (algorithm, signature, validity window) and
then as its child's proof: its `aud` is the node_id of the child's issuer key
(`not_the_delegate`), and each capability the child hands on has an equal
`can` (`can_changed`) and a `with` the parent's covers
(`grants_more_than_proof`, or `wrong_realm` for another realm). The root of the
chain is checked against the policy: `not_the_issuer` includes a chain whose
every link holds but whose root is another issuer.

What the child hands on is not every capability it names:

- With a request (a realm and a procedure), exactly one capability answers
  it: the first in `cap` order that covers the request (with the policy's
  `can`, for `realm_member_required`). That one alone is carried up the
  chain; no other capability of the token is tried, at the leaf or above
  it. A token that names a capability its parent does not cover is still
  authorized when another capability, earlier or later, answers the request
  (`ok_delegated_chain_with_an_extra_capability`).
- With no request, `ucan_required` carries every capability of the token;
  `realm_member_required` carries the first with the policy's `can`
  (`missing_capability` when none has it).
- Above the leaf, a parent carries up, for each capability its child hands
  on, the first of its own capabilities that covers it with the same `can`.

## The order of the checks

The first refusal wins, so an SDK takes the checks in this order:

1. The token's three parts, base64url, and JSON objects: `malformed`.
2. The header: `wrong_algorithm`, or `malformed` (above).
3. The types of `iss`, `aud`, `cap` and `exp`, and `iss` a did:key well
   formed for the profile: `malformed`.
4. The signature: `signature_invalid`.
5. `aud` against the verified caller: `not_the_audience`.
6. `exp` (`expired`, then `exp_beyond_max_lifetime`), then `nbf`
   (`not_yet_valid`, or `malformed` when it is not an integer).
7. With a request, the request's procedure: `procedure_without_org`.
8. The token's own capability (above): `missing_capability`, `wrong_realm`,
   `realm_name_not_canonical`. Where no capability answers, the first
   capability in `cap` order with a text `with` gives the reason, whatever
   the rest would give: the refusal its `with` is refused as an MRI with
   (`realm_name_not_canonical`, say), `wrong_realm` when it names another
   realm, and `missing_capability` otherwise, a `with` that is no MRI at all
   included.
9. The chain, a link at a time from the leaf: the shape of `prf`
   (`chain_not_linear` for more than one id, `malformed` when it is not a
   list); the parent among the proofs (`missing_proof`); the parent as a
   token (steps 1 to 4 and 6, never 5 or 8); then `not_the_delegate`; then
   the narrowing (`can_changed`, `wrong_realm`, `grants_more_than_proof`),
   whose reason, where several capabilities fail, is the first failing one in
   the child's order, each explained by the first of the parent's
   capabilities in `cap` order.
10. The root against the policy: `not_the_issuer`.
11. Last, a proof no link used: `unreferenced_proof`. So an expired token sent
    with a proof nothing names is `expired`
    (`expired_before_unreferenced_proof`).

## A provider's answers

A gated procedure whose token is refused answers `unauthorized` (a CALL's
provider error, or a STREAM_OPEN refused), except `unreferenced_proof`, which
answers `malformed_frame`. An open procedure ignores any token.

## The JSON

Byte strings (node ids, key ids, realm ids) are lowercase hex; tokens are
their text as they travel; `now` is seconds; `verdict` is `ok` or the
refusal's name.
